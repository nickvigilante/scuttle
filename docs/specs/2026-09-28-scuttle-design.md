Sections 2 through 10 were drafted autonomously overnight from the decisions recorded below and from read-only research against coder/coder `main` at `d1597a583b`.

## Intent

scuttle is a personal, unofficial, full-screen terminal client for Coder Agents, written in Rust on Ratatui.
Its author wants to use it every day in place of the web UI, the way he uses Claude Code today.
It talks to a Coder deployment only through the public REST and WebSocket API, using the user's own session.

Success means the author uses scuttle as his daily Coder Agents client for two consecutive weeks after milestone M2, and at least two other Coder employees try it.
Daily use by its author is also the maintenance strategy: the previous Go TUI (`coder exp agents`) was removed in coder/coder#25190 because nobody used it, not because its API integration broke.

### What the author asked for

- One chat at a time, plus fast jumping between chats, with subagents nested under their parent.
- Monitoring of workspace limits and AI spend limits.
- Viewing and changing Agents-related settings: personal prompt, skills, preferred models, and similar.
- A look and feel comparable to Claude Code and Pi, with the chat output given as much of the screen as possible.
- Configuration through slash menus and commands.
- Rust and Ratatui, because Rust is the author's stronger and preferred language.
- A Swagger-generated Rust SDK in a clearly unofficial repo, regenerated by CI for any coder/coder tag, branch, or SHA.

### Assumptions made while drafting

- macOS and Linux are the supported platforms for v1; Windows may work but is untested.
- The target deployment is a Coder deployment that tracks main, which runs close to `main`.
- Enterprise-only features (AI spend, workspace quota) are available on the author's deployment and must degrade gracefully elsewhere.

## Non-goals

- Parity with the web UI. Every feature is a deliberate choice, and anything not listed here is out of scope until the author decides otherwise.
- Admin settings (deployment prompts, providers, budgets, retention). The web UI owns those.
- Client-executed dynamic tools (`unsafe_dynamic_tools`). scuttle never declares them.
- Publishing either repo's crates to crates.io. Both repos stay on the author's personal GitHub account until Coder has weighed in.
- The non-interactive scriptable CLI tracked separately, although `scuttle-core` should not prevent it.
- The live git diff drawer from the old TUI. It is a candidate for after v1.

## 1. Architecture and repos (approved)

Two personal GitHub repos, both unmistakably unofficial.

### `unofficial-coder-sdk-rs`

A Cargo workspace with two crates.

- `coder-api-gen` is 100% progenitor output, never edited by hand, and owned by CI.
- `coder-sdk` is hand-written and is the only crate applications depend on. It re-exports the generated types, adds WebSocket streams, overrides the fields the spec describes incorrectly, wraps the one lossy endpoint, and handles authentication.

Section 7 describes the generation pipeline.

### `scuttle`

A Cargo workspace with two crates and one binary.

- `scuttle-core` is a headless engine with no terminal code. It owns transcript state, stream assembly, the slash command registry and parser, the settings model and its precedence rules, density decisions, and the usage and limits model.
- `scuttle-tui` owns rendering, the composer, menus, mouse handling, the clipboard, and `$EDITOR` handoff.
- The `scuttle` binary wires the two together and depends on `coder-sdk` pinned by git revision.

### Data flow

Server events arrive through `coder-sdk` and are translated into `core` events.
The `core` reducer is the only thing that mutates application state.
`tui` renders state and translates keys and mouse input into `core` commands.
`core` executes commands by calling `coder-sdk`, and results come back as events.
`core` never touches the terminal, and `tui` never calls the API.

## 2. Streaming and transcript model

This section specifies the reducer in `scuttle-core`, which is the hardest and most test-critical part of the client.
It follows the web UI's behavior in `site/src/pages/AgentsPage/components/ChatConversation/streamState.ts` and `useChatStore.ts`.

### Loading a chat

1. Fetch the chat with `GET /api/v2/chats/{id}` and a page of messages with `GET /api/v2/chats/{id}/messages`.
1. Open the WebSocket `GET /api/v2/chats/{id}/stream` with `after_id` set to the highest durable message ID already loaded.
1. The server sends a snapshot: `message` events for every message after `after_id`, then `queue_update`, `status`, `error` or `action_required` when applicable, `retry` when present, `preview_reset`, and finally a replay of in-flight parts for the current generation starting at `seq` 1.
1. After the snapshot, the stream stays open indefinitely; it does not close when a turn finishes.

### Framing

Each WebSocket text frame is a JSON array of up to 256 `ChatStreamEvent` values, so the client must iterate every frame.
The client never sends messages on this socket.
The read limit is 4 MiB per frame, matching the Go SDK.

### State

The reducer keeps, per open chat:

- `messages`: durable `ChatMessage` values keyed by their `int64` ID, ordered by ID.
- `live`: the in-progress assistant turn, made of text blocks, reasoning blocks, tool calls keyed by `tool_call_id`, tool results keyed by `tool_call_id`, and sources deduplicated by URL.
- `live_cursor`: the current `(history_version, generation_attempt)` pair and the last applied `seq`.
- `status`, `last_error`, `retry`, `queued_messages`, and `action_required`.
- `pending_history`: a buffer used only during a `history_reset`.

### Event handling

| Event                                 | Reducer behavior                                                                                                                                                                                                                                                                   |
|---------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `message`                             | Upsert by ID. If it is an assistant message, clear `live`, because the durable message now contains that content.                                                                                                                                                                   |
| `message_part`                        | Ignore parts whose `(history_version, generation_attempt)` is older than `live_cursor`. A newer pair resets `live`. Apply parts in `seq` order; a gap means the stream is broken, so reconnect. Apply per-type accumulation rules below.                                            |
| `status`                              | Set `status`. On `waiting`, drop any late parts.                                                                                                                                                                                                                                    |
| `error`                               | Set `last_error` and clear `live`.                                                                                                                                                                                                                                                  |
| `retry`                               | Set `retry` for display (attempt, delay, reason) and clear `live`.                                                                                                                                                                                                                  |
| `queue_update`                        | Replace `queued_messages` with the authoritative list.                                                                                                                                                                                                                              |
| `action_required`                     | Record the pending tool calls. scuttle does not declare dynamic tools, so this only occurs for chats created elsewhere; show it and offer interrupt.                                                                                                                                  |
| `preview_reset`                       | Clear `live`.                                                                                                                                                                                                                                                                       |
| `history_reset`                       | Start buffering `message` events into `pending_history` until the next non-`message` event, then replace `messages` with the buffer in one step.                                                                                                                                     |

Per-part accumulation, matching the web UI:

- `text` and `reasoning`: the `text` field is a delta; append to the last block of the same kind or start a new block, and skip whitespace-only deltas.
- `tool-call`: a full `args` value replaces the accumulated arguments; otherwise append `args_delta` to a raw string and parse it as partial JSON for display. Skip parts with `provider_executed`.
- `tool-result`: `result_reset` discards the accumulated result; `result` or `is_error` marks it final; otherwise append `result_delta` and `reasoning_delta`, and drop the reasoning once the result is final.
- `source`: deduplicate by URL.
- `file`: keep only parts that have `data` or `file_id`.
- All other part types never stream and only arrive inside durable messages.

Durable tool calls replace their live counterparts, keyed by `tool_call_id`, so a tool call never renders twice.

### Reconnect

The Go SDK reports an abnormal close as a synthetic `error` event, and `coder-sdk` does the same.
On any disconnect or `seq` gap, clear `live`, keep `messages`, and reconnect with exponential backoff (starting at 500 ms, capped at 10 s, with jitter), passing the highest durable message ID as `after_id`.
The status line shows "reconnecting" while this happens.

### The chat list

`GET /api/v2/chats/watch` is a separate WebSocket that sends one `ChatWatchEvent` per frame with no snapshot on connect.
scuttle loads the list with `GET /api/v2/chats` first, then applies watch events.
Kinds are `status_change`, `summary_change`, `chat_summary_change`, `title_change`, `created`, `deleted`, `diff_status_change`, `action_required`, and `context_dirty`.
`deleted` also fires on archive, once per member of the chat family, and `created` fires on unarchive.
Subagent chats are included and are identified by `parent_chat_id`.
Subagent nesting is at most one level deep, because child chats cannot create subagents, so the tree is always parents with a flat list of children.

## 3. Rendering and interaction

### Layout

The screen has three regions, top to bottom:

1. The transcript, which takes all remaining height.
1. The composer, which grows with its content up to a configurable maximum (default 10 lines), then scrolls.
1. The one-line status footer (section 6).

Menus (`/chats`, `/model`, `/settings`, and others) render as overlays anchored above the composer and never permanently shrink the transcript.
There are no sidebars or panels.

### Welcome screen and the Codernaut

A blank chat shows a small welcome block centered in the empty transcript: the Codernaut, Coder's astronaut mascot, rendered in terminal characters, plus the deployment URL, the signed-in user, and two or three hints such as `/chats` and `/help`.
The block disappears as soon as the first message is sent, so it never costs transcript space in a real conversation.

The artwork is based on the Codernaut figure used on Coder's community website, sourced from official brand artwork rather than redrawn from memory.
It is drawn with half-block or braille characters, with a plain ASCII fallback for terminals without Unicode support.
It uses the active theme's palette, so it follows light, dark, and the colorblind-friendly Coder themes.
A local config key hides it for users who prefer a bare screen.
The mascot is decoration only; scuttle has no games or interactive easter eggs.

### Transcript rendering

- Markdown is parsed with `pulldown-cmark` and rendered by scuttle's own renderer into Ratatui lines. `tui-markdown` is still labeled experimental and is not used.
- Streaming markdown follows the approach Codex CLI uses: buffer deltas, commit at newline boundaries, re-render only the live tail, and cache wrapped lines for finished messages.
- Code blocks are highlighted with `syntect` and `two-face`, loaded lazily on a background thread so startup is not delayed; unhighlighted code renders until the syntax set is ready.
- Every rendered block records its screen rectangle so mouse clicks can be mapped to blocks.

### Tool call and reasoning density

Each tool call renders in one of three modes: `expanded` (full arguments and output), `summary` (one line with status marker and a one-line result summary), or `hidden` (a count folded into the previous line).
The default is `summary`.

The effective mode for a block is decided in this order:

1. A per-block toggle the user applied in this session with a click or a key.
1. The server display preferences from `GET /api/v2/users/{user}/preferences`: `thinking_display_mode` for reasoning, `shell_tool_display_mode` for shell tools, `code_diff_display_mode` for diffs, and `collapse_assistant_steps` for multi-step assistant turns. `auto` maps to `summary`.
1. Local per-tool overrides in `config.toml`, keyed by tool name, for tools the server preferences do not cover.
1. The built-in default.

The four server-backed preferences are never stored locally; changing them writes to the server after the web UI confirmation described in section 5.

### Mouse

Mouse capture is on by default; `/mouse` toggles it and the choice persists in `config.toml`.
With capture on:

- Clicking a tool call or reasoning block toggles it between expanded and its default mode.
- Clicking a code block copies it to the clipboard and shows a brief "Copied" notice in the status footer.
- The wheel scrolls the transcript.

Capture disables the terminal's native text selection; the terminal's bypass modifier (usually Shift, or Option in iTerm2 and Terminal.app) still selects text, and `/mouse` documents this.
Mouse capture is turned off before handing the terminal to `$EDITOR` and restored afterward.

### Clipboard

Copy uses a layered strategy modeled on Codex CLI:

1. `arboard` for the native clipboard when running locally, keeping the handle alive for the life of the process, because X11 and some Wayland compositors drop the contents when the writer exits.
1. OSC 52 when running over SSH, capped at 100,000 bytes.
1. Inside tmux, the tmux clipboard path in addition to the above; scuttle warns once if tmux's `set-clipboard` is not `on`.

Terminal.app and VTE-based terminals do not support OSC 52, so over SSH on those terminals copy fails with a clear message rather than silently.
`/copy` copies the last assistant message as raw Markdown, and `/copy <n>` copies the nth code block in it.

### Composer

- Multi-line editing uses `ratatui-textarea` 0.9, the fork maintained under the Ratatui organization. The original `tui-textarea` does not support Ratatui 0.30.
- The send key follows the server's `agent_chat_send_shortcut` preference: `enter` sends with Enter and inserts a newline with Shift+Enter; `modifier_enter` does the reverse with Cmd or Ctrl+Enter.
- Shift+Enter is only distinguishable from Enter in terminals that support the kitty keyboard protocol, which scuttle enables with crossterm's keyboard enhancement flags. Alt+Enter and Ctrl+J always insert a newline as a fallback.
- Bracketed paste is enabled, and pasted text is inserted verbatim.
- Ctrl+G opens `$EDITOR` (falling back to `$VISUAL`, then `vi`) on the composer contents; saving returns the text to the composer without sending it.
- Up and Down cycle through previously sent messages when the cursor is on the first or last line. History is kept in memory per session and optionally persisted to the local data directory, controlled by a config key.
- `@path` or `/attach <path>` uploads a local file with `POST /api/v2/chats/files?organization=<org>` and adds a `file` input part referencing the returned ID. The server accepts JSON, PDF, GIF, JPEG, PNG, SVG, WebP, CSV, Markdown, and plain text up to 10 MiB, and at most 50 attachments per chat; scuttle checks size and type before uploading.

### Queue and interrupt

- Sending while the agent is working uses `busy_behavior` from the local config, defaulting to `queue`, the server's default.
- Esc interrupts the current run with `POST /api/v2/chats/{id}/interrupt`. Pressing Esc on an idle chat does nothing.
- Queued messages appear dimmed below the live turn. `/queue` lists them and can delete one (`DELETE /chats/{id}/queue/{qid}`) or promote one (`POST .../promote`).
- A `429` on send means the queue is full (default maximum 20) and a `409` means the chat cannot accept messages in its current state; both show inline, and the composer keeps the text.

### Plan mode and questions

- `/plan` toggles plan mode with `PATCH /api/v2/chats/{id}` (`plan_mode: "plan"` or `""`); for a blank chat it is sent with the first message.
- In plan mode the agent can call the server-side `ask_user_question` tool, which ends the turn. scuttle renders its questions as a selectable menu with the given options plus "Other".
- Answers are sent as an ordinary user message in the format the web UI uses: the chosen label or `Other: <text>` for one question, and one `N. <header>: <answer>` line per question for several.
- When the agent proposes a plan, an "Implement the plan" action sends that text and clears plan mode, matching the web UI.

### Keybindings

Defaults follow Claude Code where an equivalent exists, and every binding is remappable in `config.toml` and through `/keybindings`.

| Action               | Default                        |
|----------------------|--------------------------------|
| Send or newline      | Per `agent_chat_send_shortcut` |
| Interrupt            | Esc                            |
| Open `$EDITOR`       | Ctrl+G                         |
| Open `/chats`        | Ctrl+R                         |
| Toggle focused block | Ctrl+O                         |
| Scroll transcript    | PageUp, PageDown, wheel        |
| Jump to latest       | End                            |
| Quit                 | Ctrl+C twice, or `/quit`       |

## 4. Slash commands and menus

Typing `/` at the start of an empty composer opens a fuzzy-filtered menu of commands, grouped as client commands, chat commands, and skills.
Every command also works when typed in full and sent.

### Command set

| Command                   | Scope            | Behavior                                                                                                    |
|---------------------------|------------------|-------------------------------------------------------------------------------------------------------------|
| `/chats`                  | Client           | Fuzzy menu of chats, subagents nested under parents; Enter opens, other keys archive, rename, or pin.       |
| `/new`                    | Client           | Opens a blank chat.                                                                                         |
| `/workspace [name]`       | Chat             | Attaches a workspace with `PATCH /chats/{id}` (`workspace_id`), or detaches with `none`.                    |
| `/model`                  | Chat             | Picks the model for the next message from `GET /organizations/{org}/chats/models`.                           |
| `/plan`                   | Chat             | Toggles plan mode.                                                                                          |
| `/compact`                | Chat (server)    | `POST /chats/{id}/compact`, allowed only on idle or errored chats.                                          |
| `/clear`                  | Chat (server)    | `POST /chats/{id}/clear`, which resets model context and keeps the transcript.                              |
| `/title [text]`           | Chat             | Sets the title, or proposes one with `POST /chats/{id}/title/propose` for confirmation.                     |
| `/queue`                  | Chat             | Lists, deletes, or promotes queued messages.                                                                |
| `/attach <path>`          | Chat             | Uploads an attachment.                                                                                      |
| `/copy [n]`               | Client           | Copies the last message or its nth code block.                                                              |
| `/usage`                  | Client           | Opens the usage view (section 6).                                                                           |
| `/statusline`             | Client           | Configures the footer (section 6).                                                                          |
| `/settings`               | Server           | Opens the settings menu (section 5).                                                                        |
| `/provider-keys`          | Server           | Manages personal AI provider keys (section 5).                                                              |
| `/theme`                  | Client or server | Chooses the theme source and theme (section 5).                                                             |
| `/keybindings`            | Client           | Views and remaps keybindings.                                                                               |
| `/mouse`                  | Client           | Toggles mouse capture.                                                                                      |
| `/help`                   | Client           | Lists commands and keybindings.                                                                             |
| `/quit`                   | Client           | Exits.                                                                                                      |

The web UI supports exactly two slash commands, `/compact` and `/clear`, so scuttle keeps those names and semantics.

### Skills in the menu

The web UI lists the user's skills in its `/` menu, and a skill with the same name as `/compact` or `/clear` takes precedence there.
scuttle lists skills from `GET /api/experimental/users/{user}/skills` in the same menu.
Selecting a skill inserts `/<skill-name>` into the composer as message text for the agent, exactly as the web UI does.
For the two server commands, scuttle matches the web UI's precedence.
Client command names are reserved; a skill that collides with one is reachable as `/skill <name>`.

## 5. Settings

### Server settings

`/settings` opens a menu whose sections mirror the web UI's per-user Agents settings pages.
Every write shows "This also changes your settings in the Coder web UI." and requires confirmation; a config key can suppress the prompt after the first confirmation per session.

| Section    | API                                                                                                          | Notes                                                                                                                              |
|------------|--------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------|
| Prompt     | `GET`/`PUT /api/v2/chats/config/user-prompt`                                                                 | Edited in `$EDITOR`; the server rejects more than 128 KiB.                                                                          |
| Display    | `GET`/`PUT /api/v2/users/{user}/preferences`                                                                 | The four density preferences and the send shortcut. `PUT` is a partial update.                                                      |
| Models     | `GET /api/v2/organizations/{org}/members/{user}/chats/model-overrides`, `PUT .../{context}`                   | Contexts are `root`, `general`, and `explore`. When the response's `enabled` is false the section is read-only with an explanation. |
| Skills     | `/api/experimental/users/{user}/skills` (list, get, create, update, delete)                                  | Edited in `$EDITOR` as `SKILL.md` with YAML frontmatter. Experimental API; see section 8.                                          |
| Compaction | `GET /api/v2/chats/config/user-compaction-thresholds`, `PUT`/`DELETE .../{modelConfig}`                       | Threshold percentages per model.                                                                                                    |
| Debug      | `GET`/`PUT /api/v2/chats/config/user-debug-logging`                                                          | Read-only when forced by the deployment or when the user toggle is not allowed.                                                     |
| Appearance | `GET`/`PUT /api/v2/users/{user}/appearance`                                                                  | Theme and theme mode. `PUT` requires `terminal_font`, so scuttle sends back the current value unchanged.                            |

Skill names must match `^[a-z0-9]+(-[a-z0-9]+)*$`, content is limited to 64 KiB, and a user may have at most 100 skills; scuttle validates these before sending and shows the server's error on `400` or `409`.
The admin-only settings (system prompt, plan-mode instructions, retention, providers, budgets) are not exposed.

### Local settings

`~/.config/scuttle/config.toml` holds only TUI-specific settings: theme source and custom palette, keybindings, status line fields and warning thresholds, per-tool density overrides, mouse capture, default busy behavior, composer height, history persistence, and the server-write confirmation behavior.
The schema has no field that can hold a secret.
At load time, any key named `token`, `secret`, `password`, `api_key`, or `apikey`, or ending in `_token`, `_secret`, `_password`, or `_key`, is rejected with an error naming the key, so the file is always safe to keep in a dotfiles repo.
Commands that change local settings write the file immediately, preserving comments and formatting with `toml_edit`.

### Themes

`/theme` chooses one of three sources, stored locally:

- `coder` uses the appearance setting. In `single` mode it uses `theme_preference`; in `sync` mode it picks `theme_light` or `theme_dark` based on the detected terminal background. scuttle ships terminal palettes for all six Coder themes: `light`, `dark`, `light-protan-deuter`, `dark-protan-deuter`, `light-tritan`, and `dark-tritan`.
- `terminal` uses the terminal's 16 ANSI colors so the user's terminal color scheme applies, with light or dark chosen from the detected background.
- `custom` uses a palette defined in `config.toml`.

The terminal background is detected with `terminal-colorsaurus` before the event loop starts, because the event reader would otherwise consume the terminal's reply.
Changing the Coder theme from scuttle is a server write and shows the web UI confirmation.

### Session and authentication

- scuttle reads the deployment URL and session token the `coder` CLI stored at `coder login`, from the OS keyring on macOS and Windows or from the CLI's config directory on Linux. The exact keyring service name and value format must be confirmed against `cli/sessionstore` before implementation (see open questions).
- `CODER_URL` and `CODER_SESSION_TOKEN` override the stored values.
- scuttle never writes a credential. When the token is missing or rejected with `401`, it tells the user to run `coder login`.
- The token is held as `secrecy::SecretString` and exposed only when building a request, and the header value is marked sensitive.
- WebSockets authenticate with the same `Coder-Session-Token` header as REST requests, using `reqwest-websocket` on the same `reqwest::Client`.

### Provider API keys

`/provider-keys` lists providers from `GET /api/v2/users/{user}/ai-provider-keys`, showing for each whether a personal key is set, whether a provider key exists, and whether BYOK is enabled.
The API never returns a key, only its presence.

The goal is masked key entry inside scuttle with the same security properties as the web UI.
Entry uses `PUT /api/v2/users/{user}/ai-provider-keys/{providerID}` with `{"api_key": ...}`, and removal uses `DELETE`.
The following are acceptance criteria; if any cannot be met reliably on the author's terminals, v1 falls back to showing status plus a command that opens the web UI's API keys page.

- The key is typed or pasted into a dedicated masked prompt that is never part of the transcript, the composer, the sent-message history, or scrollback.
- The key is held in a `Zeroizing` buffer with capacity reserved up front, and never passes through a regular `String`.
- A bracketed paste into the prompt goes straight into the masked buffer and cannot reach the composer.
- The key is never logged, including in debug HTTP logs, and never written to disk.
- scuttle refuses to send a key over plain `http://` unless the host is a loopback address.
- The server's own checks (non-empty, at most 10 KB, no surrounding whitespace) are applied client-side first so errors never echo the key.
- A one-line note explains that the key is encrypted at rest only if the deployment has enabled database encryption.

## 6. Usage and limits

### Status footer

The footer is one line.
`/statusline` chooses which fields appear and in what order, stored locally.

| Field       | Source                                                                                                                                  |
|-------------|-----------------------------------------------------------------------------------------------------------------------------------------|
| `model`     | The chat's `last_model_config_id`, resolved to a display name through the models list.                                                 |
| `workspace` | The chat's `workspace_id`, resolved to a name.                                                                                          |
| `status`    | The chat status, with retry and reconnect states.                                                                                      |
| `context`   | Tokens used against the context limit, computed as the web UI does (below).                                                             |
| `cost`      | `GET /api/v2/chats/{id}/cost`, in micros, for the whole chat tree.                                                                       |
| `spend`     | `GET /api/v2/users/{user}/ai/spend`: `current_spend_micros` against `effective_budget.spend_limit_micros`.                              |
| `quota`     | `GET /api/v2/organizations/{org}/members/{user}/workspace-quota`: `credits_consumed` against `budget`.                                  |
| `queue`     | The number of queued messages.                                                                                                          |

The default fields are `model`, `context`, `spend`, and `status`.
Context usage follows `chatHelpers.ts` in the web UI: take the latest message with `usage`, add input, output, cache read, cache creation, and reasoning tokens, and compare against `context_limit`, stopping at a `chat_cleared` boundary and using the compaction tool result's estimate at a `chat_summarized` boundary.

Threshold warnings are off by default.
When enabled for a field, crossing its threshold (for example 80% of budget) shows the field highlighted even if it is not in the footer's field list.

Spend and quota refresh every 60 seconds and after each completed turn; cost refreshes after each completed turn.
Money is stored in integer micros and formatted only for display.

### `/usage`

An overlay with the full picture: spend for the current period with its start and reset time (`period_end`), the budget and whether it comes from a user override or a group, the current chat's cost and request counts including unpriced requests, context usage, and workspace quota.
A `null` `effective_budget` means unlimited, and a quota `budget` of `-1` means no quota applies.

## 7. The SDK and its pipeline

### Generation

The pipeline is a GitHub Actions workflow in `unofficial-coder-sdk-rs`, with top-level `permissions: {}` and only the permissions each job needs.

1. **Trigger:** `workflow_dispatch` with a tag, branch, or SHA input, and a daily schedule that checks coder/coder releases and runs for any new tag.
1. **Fetch:** download `coderd/apidoc/swagger.json` at that ref.
1. **Convert:** Swagger 2.0 to OpenAPI 3 with `swagger2openapi`.
1. **Patch:** run the patch script, which applies general rules and writes a log of every change. The spike's script and log are preserved in `docs/research/sdk-spike/`.
1. **Fix raw JSON fields:** run a small Go program against the same coder/coder ref that uses reflection over `codersdk` to list every `json.RawMessage` and `[]byte` field, and rewrite those properties to free-form JSON or base64 strings. The spec alone cannot tell them apart from real integer arrays.
1. **Generate:** progenitor 0.15 produces `coder-api-gen`.
1. **Verify:** `cargo build`, `cargo clippy`, and `cargo test`, including smoke tests.
1. **Publish:** open a pull request containing the regenerated crate, the patch log, and the coder/coder SHA recorded in crate metadata.

A change in which patch rules fire, or a large change in their counts, is flagged in the pull request description, because it means the spec changed shape.
Patch rules are deleted as the corresponding the upstream Swagger annotation fixes fixes land upstream.

### Patch rules found by the spike

| Rule                                                             | Count | Upstream fix     |
|------------------------------------------------------------------|-------|------------------|
| Drop enums that narrow a referenced enum type                    | 54    | upstream Swagger fix 1 |
| Treat `json.RawMessage` and `[]byte` as free-form or base64       | 10    | upstream Swagger fix 2 |
| Collapse multi-media request bodies and map odd media types       | 8     | None needed      |
| Merge or pick among multiple success responses                   | 2     | None needed      |
| Move `format` from arrays to their items                         | 2     | upstream Swagger fix 6 |
| Deduplicate enum values                                          | 2     | upstream Swagger fix 5 |

The openapi-generator-only rules (header `example`, undeclared path parameters, the `_` enum variant) are not needed for progenitor but are also tracked in the upstream Swagger annotation fixes.

### The hand-written layer

`coder-sdk` adds:

- `stream_chat(chat_id, after_id) -> impl Stream<Item = Result<ChatStreamEvent>>`, flattening the batched frames.
- `watch_chats() -> impl Stream<Item = Result<ChatWatchEvent>>`.
- Session discovery and a `Client` constructor that sets the token header.
- A wrapper for `GET .../templateversions/{name}/previous` that maps `204` to `None`, because the generated client can only model `200`.
- Typed errors that preserve the server's `codersdk.Response` message and validations for display.
- A `server_version()` check against `GET /api/v2/buildinfo`, used for the skew warning in section 8.

## 8. Errors and degraded modes

- **Open-source deployments:** routes that exist only in Enterprise return `404`. The spend and quota fields and the `/usage` sections for them are hidden, not shown as errors.
- **Unlicensed Enterprise features:** return `403` with a message; scuttle hides the field and shows the server's message once in `/usage`.
- **Admin-controlled switches:** personal model overrides disabled (`403`), BYOK disabled (`403`), and debug logging forced by the deployment (`409`) render their sections read-only with the server's explanation.
- **Experimental skills API:** it lives under `/api/experimental` and may change without notice. Failures in the skills section never affect the rest of scuttle, and the SDK pipeline's pull request diff is the early warning.
- **Version skew:** at startup scuttle compares the server version from `/api/v2/buildinfo` with the coder/coder ref the SDK was generated from, and shows a one-line warning when the server is newer by more than a minor version.
- **Authentication:** a `401` anywhere stops background refreshes and shows one message telling the user to run `coder login`.
- **Connectivity:** stream and watch sockets reconnect with backoff as described in section 2; REST failures show inline and never discard composer text.
- **Stuck chats:** when a chat is stuck in an invalid state, the chat view offers the recovery action `POST /chats/{id}/reconcile-invalid`, which moves it to `error` so it can accept messages again.
- **Panics:** a panic hook restores the terminal (leaving the alternate screen, disabling mouse capture, raw mode, and keyboard enhancement) before printing the error.

## 9. Testing

- **Reducer tests in `scuttle-core`:** recorded stream fixtures (JSON arrays of real frames captured from the Coder deployment) drive the reducer, and tests assert on resulting state. Required cases include `seq` gaps, stale generation attempts, `preview_reset` mid-turn, `history_reset` after an edit, reconnect with `after_id`, queue updates, retry, interrupt, and tool calls whose arguments stream as partial JSON.
- **Property tests:** reordering or duplicating `message` events never changes the final durable transcript.
- **Rendering snapshots in `scuttle-tui`:** `ratatui`'s `TestBackend` with `insta` for layouts, density modes, themes, and narrow widths, plus a `vt100`-backed harness for escape-sequence behavior.
- **SDK smoke tests:** a `coderd` container from the matching coder/coder image exercises the REST endpoints scuttle uses, with the stream and watch sockets tested against a local WebSocket server replaying fixtures.
- **End to end:** `portable-pty` or `expectrl` drives the real binary against the same container, covering launch, sending a message, streaming, `/chats`, and quitting cleanly. Chat generation needs an LLM, so the end-to-end setup points the deployment at a local OpenAI-compatible mock provider.
- **Fixture capture:** a developer-only `scuttle record <chat-id>` subcommand writes raw stream frames to a file, with tokens and file contents redacted.

## Open questions

1. **Session storage format:** the `coder` CLI's keyring service name, account, and stored value format (the Go keyring library base64-encodes values on macOS with a `go-keyring-base64:` prefix), and the Linux file location, must be confirmed from `cli/sessionstore` before M0 ends.
1. **`client_type`:** chats record `ui` or `api`. It is not yet known what the web UI does differently for each; M0 should find out before scuttle picks one.
1. **Command and skill precedence:** matching the web UI means a skill named `compact` shadows `/compact`. Confirm this is the desired behavior in a terminal client.
1. **Ctrl+R for `/chats`:** it matches shell history search, but Claude Code uses a different binding. Confirm the default.
1. **Local mock provider for end-to-end tests:** choose between a small custom OpenAI-compatible server and an existing mock, and confirm a Docker `coderd` can be configured to use it.
1. **Diff viewing:** the old TUI had a diff drawer. Decide after M2 whether a `/diff` view is wanted.
1. **Codernaut artwork:** the mascot is Coder brand material. Where to get the source artwork, and whether an unofficial tool may use it at all, are questions for Coder alongside the repo naming question.
